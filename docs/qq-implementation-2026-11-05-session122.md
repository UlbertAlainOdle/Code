# 第122轮：全部停止后旧安排从聊天历史回流，只读定位

日期：2026-11-05，America/New_York。按用户提供的新聊天实例检查原因；开工第121轮567项指纹一致，业务仍121r6/328项冻结、193份测试文件保持。本轮没有修复业务、重启、改配置或操作真实事件。

## 结论及实际证据

本次“全部忘掉”确实完成了一次6条个人事件的事务停止，操作会话为done，原6条当前仍为suppressed。旧截止安排没有恢复，也没有换编号重新建成活动事件。因此默认事件列表退出是实际生效，不是仅生成成功文案。

截止细节通过另一条路径继续可用：停止前的一条主动私聊已经把它写入原聊天。该主动消息的归档仅带proactive标记，没有qq_episode事件来源依赖，QQ上下文来源表中也没有它的来源快照。`proactive_runtime.py`的QQ投递保存原聊天和时间，但没有像普通QQ答复一样登记工作事件依赖；`QQContextSalience.project`仅在已有来源快照时执行事件有效性核验，没有来源的条目会继续进入普通历史选择。

使用实际归档、实际`QQPersonEvents.filter_history`与`QQContextSalience.project`做保守选择器重放，并特意把所有带事件快照的条目都判为不可用，该主动提醒仍被选入。此结果证明现有过滤存在这条回流通道；不是截获的真实供应商请求，也没有新调用模型。

停止后的第一条异常答复元数据没有有效事件引用；后续答复只关联新讨论主题，没有关联被停止的截止卡。这几条实际答复的长期记忆召回均为disabled、选中0条。旧信息被聊天历史提供后，又能以新的助手答复保存，形成继续引用的循环；仅核对旧事件是否还在默认列表不能发现这类污染。

列表里后来出现的同名“小目标”卡是新编号，来源是用户后续的新发言，旧卡仍停止。这反映当前自动话题采集继续运行，与旧截止信息从助手历史回流须分别判断，不能把两个现象都归为旧卡重新激活。

## 原因与修复方向

回执执行的是停止自动使用和跟进，保留原聊天和独立长期记忆，实际没有物理删除卡片正文。但保留档案不应意味着被要求遗忘的内容仍可自动参与回答；此次持续主动引用属于实现漏项，不能用“原聊天保留”解释为正常行为。

后续修复需要共同覆盖：

1. 主动消息与普通回答使用同一来源/控制依赖，停止后旧主动提醒的派生上下文也失效。
2. 从历史转述出来的回答继承实际引用的来源依赖，不能因被模型重说一次就成为无来源的新事实。
3. 对旧无标签消息采用明确的保守历史边界，并处理已经污染的近期派生上下文；原档案可保留，不恢复已过期来源。
4. “可自然讨论新发言”“新建当前话题”“恢复旧事件及自动跟进”分开处理，不能用模型自己的复述作为重建依据。
5. 验收增加“事件停止→无关普通聊天→不再夹带旧安排”，同时覆盖主动提醒与多轮转述。第121轮单卡预览/确认/列表验收仍是真实通过，但不足以证明所有历史渠道均已遗忘。
