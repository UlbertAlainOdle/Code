# 语音退出与本地聊天模型资源检查

2026-10-10，本机 RTX 4090 24564 MiB、物理内存 31.78 GiB。

## 本次发现与修正

检查时项目聊天后端已关闭，8000 无监听，但 WSL 中的本项目 vLLM-Omni 进程仍监听 8091，GPU 总占用为 11166 MiB。已核验运行目录、控制器所有权 token 和进程组，关闭这一残留服务后，GPU 总占用降至 3127 MiB。没有终止其他 WSL 程序，也没有执行全局 WSL 关闭。

原代码已注册 FastAPI shutdown 和 atexit 清理；直接关闭终端、强制终止进程时，这些回调可能不运行。现增加独立 Windows 退出守护：

- 持有后端和 WSL 启动进程的真实 Windows 句柄，同时验证进程创建时间；PID 被重用不会把新程序当成旧后端。
- 任一受监测进程退出，调用标准库清理脚本，先验证本次启动的 Linux 进程所有权，再向对应进程组发送 SIGTERM。
- 超时仍未退出时，只强制结束此前记录且创建时间仍一致的进程组成员，不按端口或进程名称批量杀进程。
- 启动时必须确认守护已就绪；准备阶段守护消失时拒绝启动语音服务。
- 正常卸载也等待守护退出。WSL 环境、编译缓存、模型文件和用户设置不会删除。

语音进程结束与 `VmmemWSL` 消失是两个层次。后者代表 WSL 虚拟机资源；Linux 终端、其他服务和缓存也可能让它保持运行。WSL 有空闲关闭和缓存回收设置，但不能仅凭任务管理器中这个名称判断语音仍在推理。[微软 WSL 配置说明](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)

如果确认没有其他 WSL 工作需要保留，可手动运行 `wsl --shutdown` 关闭所有发行版和 WSL 虚拟机；项目不会自动执行这个全局操作。[微软 WSL 命令说明](https://learn.microsoft.com/en-us/windows/wsl/basic-commands#shutdown)

## 与本地聊天模型共存

此前实测语音服务增加约 8015 MiB（7.83 GiB）显存。当前桌面等基线约 3.1 GiB，扣除后，24 GiB 显卡留给聊天权重、KV 缓存、临时工作区及其他 GPU 功能的容量大约 13 GiB。桌面和浏览器显存会波动，这不是保证可用的固定配额。CPU 侧还有 WSL Python 进程及文件缓存开销；32 GiB 物理内存同样需考虑。

| 方式 | 算力竞争 | 显存占用 | 等待与取舍 |
| --- | --- | --- | --- |
| 回复第一句就开始朗读，两套模型常驻 | 文字生成和语音生成重叠 | 两套常驻占用相加 | 最早出声，但可能拖慢本地文字生成 |
| 等文字回复完成再朗读，两套模型常驻 | 可避免同一轮同时推理 | 两套常驻占用仍相加 | 建议用于两套都装得下的情况 |
| 文字生成后卸载聊天模型，再加载语音 | 按轮次交替使用 GPU | 可以释放聊天权重给语音 | 当前语音冷加载约 43–55 秒，还需加聊天模型重新加载时间，不适合每轮切换 |
| 聊天模型部分层留在 CPU，语音常驻 | 仍可能存在，延后朗读可减少 | 聊天显存下降 | 文字速度和主内存压力需要重新实测 |
| 云端聊天 + 本地语音 | 没有本地聊天 GPU 推理竞争 | 主要是语音服务 | 符合前次语音速度测试的部署条件 |

“推理结束”不等于“模型卸载”：本项目 ModelRuntime 缓存聊天模型，语音闲置释放时间目前为 0，两个后端都会保留权重。单纯改变执行顺序不能解决模型装不下的问题。

要延后自动朗读，在 Voice 设置中关闭“输出第一句后开始自动朗读”（`stream_chat=false`），保留“流式音频播放”（`stream_audio=true`）；等完整文本出来后，音频仍可边生成边播放。自动朗读总开关按需要开启。手动点击播放则在希望的时点开始。

配置中的本地模型目前均为 `n_gpu_layers=100`、`n_ctx=8192`，倾向于全部层放 GPU。Qwen3 30B Q5 与语音常驻预计超过 24 GiB；Mistral 22B Q5/Q6 也非常紧张，需要改变卸载/分层策略。此判断是容量估算，尚未进行这几套模型与语音共存的真实性能测试：本次检查发现配置指向的三个 GGUF 路径不存在。

配置中的 Saya R1 文件实际存在，文件大小 8.128 GiB，比上述大模型更有可能与语音共存。文件大小不等于最终 GPU 占用，还需要算上 KV 缓存和运行空间；不能据此承诺 8192 上下文、3D 显示等同时开启时一定装得下。

此次只修正退出清理，未修改聊天模型路径、GPU 层数或语音自动朗读偏好。后续若使用本地聊天，建议先选择能在约 13 GiB 总预算内运行的配置，再测试文字速度和语音 RTF。前次语音约 6.4 倍实时的结果不能直接视为与大聊天模型并发时的成绩。
