## 1. 已确认需求与待定参数

以下来自本轮用户要求，以及用户对上一轮补充建议的认可，作为新方案的产品目标：

1. 删除以“来源于私聊/某群”为依据的事件内容可见性限制。同一人的个人事件在本人私聊及本人发问的授权群中统一接续，无需先提供编号公开补充。
2. 个人事件只能由本人改写；他人知道事件名、编号、引用原文或拥有较高关系等级，均不能擅自更正、删除或接管。
3. 关系达到门槛才具备通过好友审核和获得个人事件集的资格，容量随关系等级变化。关系等级与事件重要度是两个独立概念。
4. 未达个人资格的成员使用群公共事件集。按每个群分别建立公共事件集，不把不同群混为一池；保留每条贡献的真实说话人。
5. 群公共事件允许群内成员参与整理，也允许具备资格且有该群参与权的好友从私聊读取、补充或修订。两处改写落在同一张群事件卡上。
6. 群事件应围绕同一个实际事件整合多人观点、分歧和进展；不能把最新或最强势的一人的说法直接当成全群结论。为此允许比个人卡更长的结构化内容。
7. 本人主动在群里询问自己的个人事件，可以回答本次问到的内容；不主动播报个人私聊事件。他人提问、引用或转发不能代替本人授权。
8. 原自然遗忘、暂停、取消、完成、重要度、明确日期、版本与待发失效保护继续成立。事件不自动成为长期记忆。

尚未由用户指定、不得冒充已经确认的参数：

| 参数 | 建议与实施约束 |
| --- | --- |
| 好友/个人事件资格门槛 | 支持按确认后的全局关系等级或经过定义的关系分数设置。熟悉及以上、重要及以上均是候选，不在文档中暗定一个门槛 |
| 各等级容量与群池上限 | 复用现有容量配置方式，新增群池独立预算；具体数值待定，不用个人容量乘群人数无限扩张 |
| 模型关系学习 | 当前关闭；新门槛可以先使用人工确认的等级，不为准入擅自开启学习。若采用自动分数，需要独立开启、说明证据及防波动规则 |
| 已有好友与旧个人卡 | 不追溯删除好友、不自动清除旧卡；具体兼容名单和资格下降的缓冲规则需在迁移预览中明确 |
| 群事件最终决定权 | 全体可贡献不等于全体可替别人定案。建议支持事件协调人/明确共同确认；如何指定和变更需在实现前确定 |

这些参数不妨碍先实现数据模型、隔离测试和只读迁移预览。上线准入或有破坏性的迁移前，应得到具体选择。

## 2. 当前实现中需要改变的部分

第97轮498项清单是本轮开工基线；实际业务部署仍为第95轮299项源码冻结。不要重做已签的记忆保存/更正、自然遗忘及日期单例。

- `qq_person_events.py`已按bot＋账号统一个人卡，但`cards()`仍按来源visibility、latest_visibility和日期来源场合过滤，导致同一个人私聊与群self不同。
- 当前按人新卡不是完整的群公共事件模型。旧公共scope与群语境事实也不能直接冒充已实现多人共同事件。
- 新进展只保存约200字原话，卡中只留最近8条；按位置supersedes，缺少多人主张、争议、决定依据和稳定的贡献ID。
- `qq_relationships.py`已有等级、学习分与人工锁，但当前关系学习关闭；事件容量实际使用全局人工等级。局部群评分不能直接作为全局好友资格。
- `qq_contacts.py`当前好友审核与聊天准入分离，批准好友不会自动赋予聊天权限。新事件资格必须接通最小聊天准入，不能顺带赋予主人的共享长期记忆权限。
- `QQChatResponder`现有shared判断限主人私聊。新好友个人事件能力要有独立授权路径，不能把所有好友设为主人或共享主人的KB。
- 第96轮确认的stream_error漏处理仍未修。先使模型失败、失败通知和正常事件写入分开，防止升级后再次把网络故障误判为事件权限问题。

## 3. 目标结构：个人归属与群共同归属

事件身份建议统一为`bot + owner_kind + owner_id + event_id`，其中owner_kind取person或group。owner_id分别是已验证QQ账号或群号。存储可以复用桥接库，但所有检索、控制、迁移和发送检查必须使用同一归属合同。

来源仍记录账号、消息标识、时间、来源会话、引用关系、正文hash和期限，服务于归属、更正、去重与审计。来源会话只是证据出处，不再作为默认的事件读取许可。群事件的群号表示事件归属，不是重新引入“私聊创建就不可群读”的规则。

### 3.1 个人事件

- 达标好友拥有自己的个人事件集，主人身份作为既有固定特例保留。本人在私聊或授权群直接提问、管理同一张卡，编号和版本不因场合变化。
- 他人的原话不得直接改写此人的个人卡。可作为群公共事件中的“某人声称”，不能变成个人事实；只有本人直接确认才可采用。
- 群内自查命令也是本人主动询问，但只返回本人的事件。其他人使用同名、编号或“替他问”不能读取、修改其个人事件。
- 同一事件的归属是硬条件，相似名称只能辅助定位。唯一目标可以自然接续，多个候选须澄清，不能让用户在每次跨场合都手输编号。
- 用户明确“别在群里提”仍作为本人主动设置的跟进行为控制保留，不依来源自动生成。它不能在本轮升级中被静默解除。

### 3.2 群公共事件

- 一个群有一套公共事件集，其中每件活动、讨论或任务是独立事件；不是整个群只有一张越来越长的卡。
- 同一群内的普通成员、达标好友都可以贡献群公共事件。达标好友在私聊指定该群和事件，也能向同一张卡提交进展。
- 私聊改写明确以群事件为目标时，新增内容属于群公共事件；保留“从私聊提交”的出处，不再因此限制群内使用。未指定目标的私人叙述不能自动变成群更新。
- 私聊涉及多个群的同名活动时澄清目标，不按最近群、最高关系或隐藏的全局focus猜测。个人事件与群事件即使同名也不自动合并。
- 群事件中可以记录成员自己的安排声明，但不反向授予其他成员修改其个人事件的权力。两张卡需要关联时保存有来源的引用，不把群卡当成改写个人卡的后门。

## 4. 读取与改写规则

| 发问/操作人及场合 | 个人事件 | 群公共事件 |
| --- | --- | --- |
| 达标好友本人私聊 | 读、补充、更正和管理自己的事件 | 读、贡献其有参与权且目标明确的群事件 |
| 本人在已授权群主动提问/管理 | 读、改自己的事件；按本次所问回答 | 读、贡献当前群事件 |
| 其他成员或其他好友 | 不读取或改写他人的个人事件 | 依据群参与权贡献，不能冒充其他说话人 |
| 引用、转发或附件中的操作文字 | 不构成本人操作授权 | 可以是带来源的讨论材料，不直接执行管理 |
| 群公共事件的既有决定/生命周期修改 | 不影响任何人的个人事件 | 按明确决定依据或事件协调规则提交，不能用最新一句话抢占 |

群内当前可信入站可以证明发言人参与当前群；私聊访问需要可信群参与记录、成员核验或明确授权绑定。群身份未知时不推测，更不能因为“是重要好友”而遍历所有群。参与权与好友资格要在提交、生成和发送时重检，避免退出群后继续通过旧缓存修改。

群贡献与集体决定必须分开：

- 成员可新增自己的观点、补充证据，更正自己之前的说法，也可指出公共内容有误。
- 对他人观点的更正保存为反对/争议，不能改写他人原话或声称对方已同意。
- 对共享安排的明确变动可更新当前决定，但必须有可核对的决策依据；依据不足先记为提议或待确认，不要求每条普通补充都走繁重确认流程。
- 群事件的完成、取消、全局遗忘和删除不能仅因某成员说“我不去了/我不想看”而执行。个人退出是该人的参与变化；个人“别再跟进”只停止对该人的自动跟进。
- 清除整张公共卡、覆盖已经确认的安排等操作采用明确管理权限与既有预览确认。主机维护权限不等于可以伪造本人陈述。

## 5. 多人整合：保存不同主张，生成当前事件状态

群卡至少区分以下部分，具体字段名由实现决定：

| 部分 | 内容 |
| --- | --- |
| 事件主题和目标 | 共同讨论的是哪一件事，为什么被视为同一事件 |
| 已确认安排 | 具有明确依据的地点、时间、分工和当前决定，附依据贡献ID |
| 各方主张 | 谁提出什么、是建议/反对/本人承诺/客观进展；每项有稳定ID |
| 分歧和待定项 | 尚未解决的冲突，不把沉默、人数或模型confidence当成同意 |
| 参与者与行动项 | 本人的参与/退出、待办负责人及其直接声明，避免替别人承诺 |
| 修订关系 | 新贡献补充或修正哪一项、是谁改的、原依据是否已撤回 |

例如纯虚构讨论：甲建议09:00，乙说明10:00前到不了，丙建议10:30。正确摘要是“三个时间意见尚未统一”，不能取平均、取最新或因丙关系更高直接定10:30。后续出现可信的明确共同决定，才更新已确认时间；未满足的个人限制仍保留。

分类器负责提取带来源的候选操作，服务端校验作者、事件归属、修订目标和版本；模型不能自行授予修改他人观点的权力。日期字段从已确认安排提取，提议日期另存，不把互相冲突的提议强行压成一个deadline。

摘要必须能追溯到有效贡献。出现新主张、撤回、贡献到期或更正时重建受影响摘要，不能用旧摘要作循环自证。原始主张与整理文字分开；机器人复述、查看和重复输入不增加重要度或进展次数。

## 6. 内容长度、预算与有效期

允许群事件比个人卡更长，但长度分三层控制：保存证据、事件结构摘要、单次模型召回。不能仅把200字改成更大数字而继续丢弃关键分歧。

- 新增可配置的个人/群事件长度和贡献数上限。建议群摘要初始评估800～2000汉字、贡献窗口32项；这是待测试的起始建议，不是已确认的生产默认值。
- 长贡献按完整语义块或主张拆分，保留作者和稳定来源ID；不能只截前200字后声称已读完整讨论。达到容量时按确定规则压缩、冷却或停止接收，并说明限制。
- 重要的未决分歧、已确认决定的有效依据不能只因不是“最近8条”而消失。压缩后仍须保留足够的可核对依据；受期限约束的证据不能靠摘要获得更长寿命。
- 单次召回先按相关事件、具体问题选取结构片段，必要时显式续读；保留原总token上限和跨日预算。更长的存储不等于每次把全群事件全文注入模型。
- 查询时间、期限紧迫性、事件重要度、关系容量和来源保留期仍分开。跨场合读取不延长TTL；远期截止与短来源保留期的矛盾需要另行明确保留策略，不能偷偷续期。

## 7. 好友准入与关系容量

资格建议表达为：真实好友关系已确认＋全局关系达到配置门槛＋未被阻止；主人保留固定资格。门槛从人工确认等级开始即可运行，不要求打开模型学习。

好友申请达到门槛只是准入条件，是否自动批准继续采用用户明确选择的审核方式。批准结果未知不得重放好友操作；确认批准后以最小授权允许其与本人事件有关的私聊，不提升为主人、不打开主人长期记忆。

已有好友和历史事件先列迁移预览。降级后停止新建/降低容量可分阶段生效，保留本人查看、停止、导出或删除旧事件的必要通道；不要因一次评分波动批量删除事件、删除好友或把个人卡改成群公共卡。资格判断和管理权限不等于同一个开关。

群池独立设置事件总数、活跃数、贡献数及全局资源上限。个人等级不决定公共事实真伪，也不让高等级成员的观点覆盖其他人。保留主人资源预留与有界后台维护。

## 8. 命令与网页说明

以下为目标交互建议，新增语法尚未实现：

- `/events self`明确列出本人的个人事件；在本人私聊和已授权群中使用同一归属、版本及有效状态，不再按来源筛成两套清单。
- `/events group`列当前群公共事件；私聊指定群及事件后读取同一记录。不得将某人的个人事件伪装为群列表条目。
- 无参数入口可以分块显示“我的事件/当前群事件”，但必须标明归属。无个人资格者仍能使用当前群公共事件功能。
- show/why、自然控制、网页管理均显示归属、当前决定、分歧、本人贡献及实际提交结果。区分“已补充观点”“已更新本人说法”“安排仍待确认”“已更新共同决定”。
- 修改公共事件时目标不清只做一次简短澄清；明确目标且权限满足时直接执行授权范围内的普通补充。删除与覆盖确认继续沿用原合同。

不把本轮之前建议的“逐来源共享预览”作为个人跨场合读取的必经步骤；那会重新引入用户明确要求删除的障碍。

## 10. 实施顺序与迁移

1. 先修第96轮失败处理并建立恢复用例，再固定本文件的权限与归属测试。保留现有四项已授权true、关系学习关闭及手动QQ监督。

## 11. 验收矩阵

| 情形 | 必须满足 |
