# QQ 独立表达与多消息回复方案

更新：表达层、默认来源隐藏及内部告警保留已在[第十轮](qq-implementation-2026-10-28-session10.md)实现并部署；多消息发送和新增可视化表达选项仍未实施。下文保留最初设计语境，不能按历史“本次仅设计”重做已交付部分。

原设计日期：2026-10-28。用户允许先提交方案；本次仅核对源码并记录设计，没有修改运行代码、配置、提示词或既有人设，没有重启服务、代发QQ消息或调用付费接口。自动新闻搜索实机已通过，证据见[进度](qq-implementation-status.md)。

## 当前原因

- `saya_app/services/qq_chat.py`的SSE适配器把全部`web_warning`作为尾注，并将`web_sources`拼成“参考来源”。因此DeepSeek安全筛选能力说明即使搜索成功也反复出现；这部分来自适配器，不完全由模型生成。
- QQ复用网页的基础提示词与回答生成器。已有`channel_identity_prompt`负责主人、群聊、权限和个人记忆隔离，缺少明确的QQ日常表达规则；改主人身份提示无法单独解决篇幅和报告风格。
- `qq_bridge.split_reply`已有按长度发送多条的基础能力，代码默认`chunk_chars=1500`、总长6000，超过总长截断。它主要按换行/字符边界切分；消费者已有有序发送及发送不明不重放规则。几百字回答自然仍是一整条。
- 新的按语意分泡、逻辑回复关联、每段回执、完整结果续读属于原QQ-03；当前严格串行门禁仍有效，不能把降低切分阈值当成QQ-03已交付。

## 1. 保留人设，叠加QQ表达规则

不改角色背景、性格、关系、主人身份、价值取向和长期记忆；不写回网页人格/风格文件。继续使用原基础提示词，在每次QQ请求叠加独立表达层；网页请求不注入。

建议表达规则：

- 把对方当作正在QQ里聊天的人，直接回应当前话题。默认一至三句话，约80～200个汉字作为软目标；问候和简单问答可以更短。
- 新闻默认挑两三件重点，说明发生了什么；不默认生成报告标题、长背景、任务进度、能力清单或结尾总结。
- 对方明确要求详细分析、步骤、代码或完整内容时允许展开，不能为短而遗漏关键条件；不擅自删掉实际未确认、失败或不确定的事实。
- 不强制卖萌、使用表情、称呼主人或每条结尾反问；称呼与语气服从原设定。
- 阅读网页和记忆可在内部执行，正常回答只呈现有用内容。后台厂家、配额和安全参数不作为日常闲聊附注。
- API和本地模型、固定研究和自主工具最终回答均需验证注入位置一致，避免某条分支仍采用网页式报告风格。

## 2. 将内部依据与QQ可见文本分开

默认QQ回复不附“参考来源”、裸来源链接和引用编号；保留已经取得的来源、访问/发布时间、读取状态、校验和失败信息作为内部证据。用户明确在本次请求中要求网址、原文或出处时可以展示所需链接；真正的查证依据不能丢弃或伪造。

实施建议：

1. 保留通用生成器的证据注入与引用校验；QQ展示适配器最后做输出投影，网页来源卡和诊断保持原行为。
2. 只隐藏已识别的能力说明，例如`search_safe_search_unavailable`、`search_region_hint_unavailable`；保留在结构化诊断/网页设置中。不把所有告警一律吞掉。
3. 搜索失败、没取得可靠资料、余额/限流导致本次无法查证时，QQ给一句自然反馈，例如“这次没查到可靠结果，晚点再试。”，不能仍假装已联网核实。需要诊断细节时再由管理入口展示。
4. 去除引用编号时只处理与已知来源对应的引用，保护数组、代码、数学编号、用户提供的网址；不能用大范围正则删除所有方括号或所有URL。
5. 不删除所有包含DeepSeek/Brave的正文，它们可能正是用户讨论的新闻主题。避免模型自己生成“参考来源”段：在QQ表达规则说明不写来源清单，必要的内部编号仍保留到引用校验完成再投影。
6. 真实记忆写入/候选确认的回执与搜索来源不同；继续保留准确的提交状态，不因简短风格误报或隐去失败。

验收：成功搜索无能力尾注和默认来源列表；模型提示仍有检索证据、内部来源仍存在；显式索取链接可获得对应地址；搜索失败可见；记忆写入回执可靠；网页和群/个人权限不变。

## 3. 多消息发送方式

目标：短回复发一条；需要展开时通常两三条，每条一层意思。可先试每条约80～160字的软目标，保持硬长度和条数预算，避免把一个句子切成多个碎片。用户明确要求详细时可适度放宽，复杂内容的剩余部分通过有权限和过期保护的续读处理。

- 一次提问先生成一个完整逻辑回答，再按段落/句子边界拆分发送；不为每个气泡重复调用模型、搜索或保存记忆。
- 短句不强拆；链接和代码不从中间截断；群聊引用和@统一处理，避免多次无意义提醒。
- 同一轮历史记为一轮，发送顺序不乱，段数受限，不随机延时营造输入状态。
- 各段确认/未知分别记录；第二条失败不能重放第一条，重启不能自动重发发送不明内容。
- 分消息改善阅读体验，不等于缩短搜索/正文读取时间。边生成边发与即时进度属于QQ-04，不能把本方案说成已经支持。

这部分按[QQ-03原计划](qq-roadmap-2026-10-26.md)实施。原QQ-01/02未完整过门禁，当前只记录设计；不提前重写发送层。

## 4. 设置边界与实施顺序

QQ表达选项应放在Settings → QQ接入，作为QQ专属偏好，避免继承网页的报告风格。建议提供“日常聊天/详细说明”“默认显示来源”“多消息回复/单条长度目标/单轮条数上限”；若支持聊天命令，继续用现有同源修订和冲突机制。具体字段在实施时确定，本轮没有新增开关或伪装已可用。

先做QQ表达层和可见附注策略的实现及兼容回归，再补真实QQ普通聊天/新闻/记忆保存/群@的观察；多消息发送等QQ-03前置验收通过后按原顺序落地。每次都保留原人设、共享长期记忆、历史隔离、厂家选择、已有开关值、监督及启动选择。

验收文件需分别记录模拟与真实结果。真实对比只需用户评价是否自然、是否过长、是否仍出现后台尾注；无需公开完整聊天记录。没有改动的源码不重复跑累计测试，真正改提示词/格式投影时覆盖API/本地/自主工具分支。
