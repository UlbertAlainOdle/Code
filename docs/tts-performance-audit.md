# 本地 Qwen3-TTS 速度检查（2026-10-09）

结论：RTX 4090 24 GB 有足够显存，当前主要瓶颈是官方 qwen-tts 0.1.1 的逐步语音编码生成，加上项目每次只提交一段文字。两段一起批量生成可以明显提高吞吐量；它与同时发出两个 HTTP 请求不同。尚未将批量方案接入日常朗读，此次仅增加独立测速脚本。

## 当前调用链

- 聊天结束后 `SayaVoice.autoRead` 才开始朗读，首段需要等待整个文本生成结束。
- `voice_settings.js` 按最多 100 字合并分句，获得整段 WAV 后才能播放；播放当前段时已经预取下一段。
- `LocalTTS.rpc` 使用互斥锁，单个常驻工作进程逐个执行请求。因此增加浏览器 HTTP 并发目前仍是后端串行排队。
- 工作进程使用 BF16 + SDPA，缓存克隆参考编码，模型在同一模式下复用。每个请求不会重新加载模型或重新编码参考声音。
- 闲置 300 秒后自动卸载；下次使用会再次启动 Python、加载权重和准备参考声音。模型权重加载本次实测约 2.4–3.8 秒，参考编码约 0.38–0.75 秒；这些不包括新工作进程导入 Python 库的时间。
- 库的 `non_streaming_mode=False` 是模拟流式文本输入，并不返回流式音频。现有项目是分段完整音频播放。

## 实测

使用本机 RTX 4090、已保存的克隆参考音色和采样设置；模型和参考编码已加载后计时。CUDA 阶段计时前后同步，全部生成实际 WAV。RTF 是生成耗时除以输出音频时长，小于 1 才表示吞吐量快于音频播放。

| 用例 | 生成耗时 | 输出音频 | RTF | PyTorch 峰值分配 |
|---|---:|---:|---:|---:|
| 一句短句，默认 24 CPU 线程 | 11.54 秒 | 6.08 秒 | 1.90 | 4408 MiB |
| 同一句，1 CPU 线程 | 14.27 秒 | 6.08 秒 | 2.35 | 4408 MiB |
| 同一句，4 CPU 线程 | 11.84 秒 | 6.08 秒 | 1.95 | 4408 MiB |
| 同一句两份，同批生成，1 CPU 线程 | 11.79 秒 | 合计 12.56 秒 | 0.94 | 4783 MiB |
| 不同文字 A（49 字），单段 | 17.63 秒 | 9.68 秒 | 1.82 | 4514 MiB |
| 不同文字 B（48 字），单段 | 22.41 秒 | 9.52 秒 | 2.35 | 4509 MiB |
| A+B 同批，默认 24 CPU 线程 | 21.22 秒 | 合计 18.40 秒 | 1.15 | 4958 MiB |
| A+B 同批，1 CPU 线程 | 19.59 秒 | 合计 18.40 秒 | 1.06 | 4958 MiB |

A+B 单段串行合计 40.04 秒；相同默认线程数下批量生成 21.22 秒，耗时减少约 47%。采样在批量和单段之间会产生差异，输出时长也略有差异；没有做正式的音色/准确率评测。这是少量实测，不是所有文本的速度保证。CPU 线程减少没有稳定的单段收益，保留现有设置。

短句单段总耗时 11.54 秒中，语音编码生成占 11.38 秒，波形解码占 0.16 秒。历史 18 段克隆音频合计 168.64 秒、生成合计 376.14 秒，RTF 中位数约 1.96。现有一段预取无法完全隐藏超过播放时长的生成耗时。

峰值分配只统计 PyTorch，不包含 CUDA 上下文、桌面和其他程序。GPU 硬件监控仍有大量显存空余，没有看到显存不足或 CPU 回退的证据。日志里的缺少 SoX 提示没有阻止这些 WAV 生成；不能凭此提示认定它是速度瓶颈。

## 建议实施顺序

更新：上述原后端问题已通过 vLLM-Omni 流式加速解决，本机长文本生成 RTF 约 0.157，真实浏览器连续播放约 93 秒无断流。最终实施与测试见 [连续朗读优化记录](tts-streaming-optimization.md)，当前无需更换 1.7B 模型。以下保留初次分析时的建议。

1. 保留 1.7B 音色，首段单独生成，采用较短的完整句子；其余每两段作为一个批次生成，按原顺序播放。限制预取窗口、停止时取消后续批次，避免一次把整篇回复投入 GPU。
2. 增加批量接口和工作进程的列表输入，而不是简单移除 RPC 锁或复制多个模型工作进程。首段不要和长段一起生成，否则会增加首次播放等待。
3. 将批量预取与有界音频缓存配合，生成可以在播放较长段时继续前进。仅增加缓存不能解决长期 RTF 大于 1。
4. 要进一步降低首包等待并提高吞吐量，评估 vLLM-Omni 的流式音频输出、批处理和 CUDA Graph 等推理优化。官方当前文档已支持 Qwen3-TTS 的 PCM / WebSocket 流式输出；部署环境和本机收益需另外验证，官方 H200 成绩不能视为本机 4090 成绩。
5. 最后再比较 0.6B Base，评估速度、克隆音色和情绪细节的取舍。模型变小不是此次首先需要采取的措施。

降低 `max_new_tokens` 主要限制最大生成长度，正常提前结束的音频不会因此自动加快；过低可能截断话语。温度、top-k、top-p 主要控制采样结果，不能指望调这些获得几倍速度。调播放速度也不会提高模型生成速度。

## 复现与结果

在项目目录执行：

```powershell
& .runtime/qwen-tts/Scripts/python.exe scripts/benchmark_qwen_tts.py
& .runtime/qwen-tts/Scripts/python.exe scripts/benchmark_qwen_tts.py --representative
```

脚本不更改语音设置，退出后释放自身模型。记录与样本位于 `.runtime/tts-benchmark/results.json`、`representative.json` 和同目录 WAV 文件。
