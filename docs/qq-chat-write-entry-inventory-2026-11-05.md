## 第139轮内置Agent静态核对

`saya_app/services/memory_v4/capabilities.py`的`register_memory_capabilities`固定注册`memory.query`、`memory.read`、`daily.query`、`time.query`、`weather.query`、`web.search`、`web.read`、`connector.read_feed`、`connector.mark_read`共9项。`core_services._memory_v4_capability_registry`逐项提供查询/读取处理器，没有传入长期记忆创建或保存处理器。`connector.read_feed`可poll并写本地attention inbox；`connector.mark_read`是access=write、confirm_each_time的收件箱标记，不能将“没有长期记忆保存工具”写成“所有工具没有写副作用”。本次没有实际调用连接器、搜索或模型。

`AgentLoop`消费调用者传入的registry，因此其类本身并不保证任何自定义registry永远无写工具。`multi_agent_chat.py`的多人物聊天仍逐个调用共用single_response；自定义人物设置role_mode=assistant、关闭工具Agent/召回，Saya分支继续共用原生成器及其后置保存条件。这两个Agent概念分开登记；当前只是源码调用链核对，不等于所有实际配置/动态注册分支已经验收。R3仍须枚举每个可达调用者和统一操作/结果身份，不能跳过。

继续顺序：先完成[实施状态](qq-implementation-status.md)记录的R2剩余门禁；R3先补Agent实际能力和全部装配分支清单，建立操作身份/冻结计划/提交结果查询的隔离合同，再逐入口转发和验证。R4先保留召回基线，R5归并不能跳过这些门禁。

## 第144轮 R3 首个隔离验收合同

优先收敛语义事件操作的近期来源。`QQEventOperations.handle` 目前将 `recent_dialogue` 的正文投影与卡片目标快照分别生成。操作快照包含目标、授权、会话、话题代次和控制版本。仅发生近期片段到期时，上述状态可能相同。操作的语义定位依据因此需要与预览一起保存。

| 阶段 | 通过条件 |
| --- | --- |
| 模型定位 | 记录本次送入的近期片段对应的来源标签或有效快照。模型返回后重验。来源单独失效时退出定位 |
| 预览投递 | 将同一依据与已冻结的目标和预览绑定。发送分段之前重验。来源失效的预览无法获得可用确认状态 |
| 用户确认 | 仍需真实送达和原有授权。事务内同时核对目标与有效来源，防止停用或失效后的旧定位继续提交 |
| 兼容与正向对照 | 显式编号和确定性批量入口继续使用其原有授权与目标快照。合法语义预览可完成确认和实际提交，已存旧预览按明确兼容规则处理 |

首批回归注入模型等待、预览发送、确认提交三个时点的来源变化。每个失败用例核对事件版本、收录状态和操作结果表。随后与聊天保存和其他读取入口的统一计划合同对照。以上为源码定位和验收设计，实施等待 R2 门禁。

## 第146轮 R3 语义事件操作的来源保护

R2 真实门禁已通过。语义事件操作按原查询记录本次使用的近期来源指纹。私聊沿用聊天投影和标签，旧未标记片段保留初次计算的有效期限。群聊按具体记录及请求者授权重验。定位模型返回、首次或续发预览、登记送达和确认事务均核对原依据。重新定位沿用仍有效的上轮依据，最多保留四组。已存旧版确定性批量计划在能重建并精确匹配时继续按原规则确认。其余旧语义计划重新提请。

接续枚举聊天写入入口的运行装配和动态工具注册，先核对明确写入与候选入口如何形成同一操作身份、冻结计划与可查询结果。然后逐入口接入并验证事务、重复提交、拒绝路径和调用者授权，完成 R3 的整体验收。

本轮复核了随正式服务启动的绑定。启用 QQ 时，`_startup_qq_bridge` 先设置旧候选回调，同一段启动代码为 Bridge 和 Responder 注入同一个 `QQMemoryManagement`。正常装配的 `/memory-save` 与建议确认均优先走主机预览。独立构造 Responder 或 Bridge 时仍可进入兼容回调，后续须用无管理器和有管理器两种装配做回归。网页 Agent 的一次请求、流式接口和共享聊天生成器均进入 KnowledgeBase 的 AgentLoop 装配。仓库里自建注册表的其他明确调用位于评估脚本，正式 Agent 仍使用上文的内置九项注册。

## 第148轮 网页重试与V4提交结果

网页请求携带32位request_id，重新生成沿用原用户消息的编号，编辑后重发使用新编号。首次请求未收到会话回执时也能凭原编号回到同一会话。多人物调度传递同一编号，自定义人物继续按原授权运行。网页保存使用 `capture_explicit_memory_result`，回执与 `/api/kb/write-result` 查询都取同一操作结果。正文或计划变化而复用旧编号时拒绝本次写入，并结束候选回退。

将147轮的记录引擎提取为 `memory_write_operations.py`，QQ兼容适配继续使用原表，网页与KnowledgeBase原生调用在memory3.sqlite3记录 `memory_write_operations`。原显式捕获与V4方法为兼容转发入口，内部存储实现继续执行原事务。嵌套写入共用外层操作，后台线程无法沿用已退出的执行标记。V4保存、更正、删除与被动候选的结果按原类型登记，已提交条目的重放只在当前版本匹配时提供正文。

本轮进一步核对调用链，当前仓库的 `process_memory_write_v4` 由显式捕获和内部代码调用，直接构造WritePipeline的其他运行脚本是评估入口。`/v4/controls` 是另一套明确控制接口。前文“V4结构化端点”的概括由此细化。

R3后续先收敛网页候选表单的CAS确认与候选状态文件失败后的恢复结果，再核对普通网页答复如何承接主机结果、原生结构化调用对实际来源的授权及版本证明。手动表单、导入、Listener和后台维护继续按各自明确用途验证。最后逐入口复核4.11并进行R3实际QQ验收。
