# 07｜最终评分与分批修复路线图

读取前六份结果，报告写入 `evaluation_results/07-final-report.md`。不得把未实测项解释为通过，本阶段不改代码。

## 执行完整度

汇总每阶段状态、执行比例、证据等级分布和阻塞。核心阶段大量 BLOCKED 时必须降低结论置信度。

## 加权评分（每项 0–5）

| 维度 | 权重 |
|---|---:|
| 聊天核心可靠性 | 20% |
| 记忆质量与隔离 | 20% |
| 数据安全与恢复 | 15% |
| 项目/目标/打卡闭环 | 10% |
| 联网研究与引用 | 10% |
| 前端可用性 | 10% |
| 性能与持续运行 | 10% |
| 媒体与外部集成 | 5% |

每项必须引用证据。存在未解决 P0 时，不得评为“可稳定使用”。

## 输出内容

1. 已可靠、应保持不动的能力；能用但需加固的能力；尚未闭环/占位能力；建议暂停扩张的区域；最值得投入的一条产品主线。
2. 合并重复缺陷：`总表 ID｜严重度｜标题｜影响｜来源阶段｜证据等级｜建议方向`。
3. 最多四批修复：Batch 0=P0/数据/启动；Batch 1=聊天—会话—记忆 P1；Batch 2=项目/打卡/联网/主要 UX；Batch 3=性能、代码拆分和低优先级体验。
4. 每批写目标、缺陷、涉及模块、禁止顺手改动范围、需重跑阶段、完成标准。
5. 发布建议四选一：仅开发者实验；个人日用但需备份；少量可信用户试用；稳定发布。
6. 最后给出不超过 500 字中文摘要，包含成熟度、最高风险、最强优势和第一批工作。
