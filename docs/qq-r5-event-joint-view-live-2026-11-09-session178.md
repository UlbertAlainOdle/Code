# R5 事件联合视图 QQ 实机验收

第178轮用户已暂停手动发送。下列脚本作为后续 R5-A 定向验收的测试输入和预期。真实目标和执行身份以该任务的预检为准。

长期记忆联合视图已另行验收及清理。这里验证两张原事件卡的联合预览、实际投递、重复确认、原编号查询和撤销。使用下列虚构材料。每条消息等完整回执，遇到无回复、权限提示、容量提示、样本进了同一张卡或预览缺字时，停在该处并发最后一条回执。先保留样本供只读对账。

## 主人私聊的个人事件

1. 发送 `/events self`，记录原清单。已有同名样本就先反馈。
2. 发送 `/context new`，收到新话题回执后发送 `这是虚构的 R5 验收材料。我的云苇展台登记演练已经完成表格核对，下一步准备登记样本。` 等回复，再发 `/events self`。记下本次新建的登记事件编号，用 `/events show 编号` 核对正文。
3. 发送 `/context new`，收到回执后发送 `这是另一个虚构的 R5 验收事件。我的云苇展台归还演练已经完成编号清点，下一步准备归还样本。` 等回复，再发 `/events self`。记下本次新建的归还事件编号，用 `/events show 编号` 核对正文。两张卡须有不同编号。
4. 发送 `/events link 登记事件编号 归还事件编号`。预览应分别呈现两条有效原话和各自原编号。复制预览末尾的完整 `/events link-confirm 操作编号`，收到成功回执后，等平时的消息冷却再重复一次相同确认。记下同一操作编号。
5. 用 `/events link-show 登记事件编号` 和 `/events link-show 归还事件编号` 分别查询。两次都应显示同一联合视图。发送 `/events link-undo 操作编号`，再发送 `/events link-result 操作编号`，应返回已撤销。重复原确认命令应继续返回已撤销。
6. 再用两条 `/events show 编号` 核对两个原事件各自仍在。把两个事件编号、操作编号和最后回执发到 Codex，保留样本等待对账。

## 原群内的共同事件

个人事件对账后，只在本人愿意用于测试、已有授权和成员权限的原 QQ 群中操作。每条测试消息及命令按该群原有规则 @ Saya。群内测试只用下列虚构材料。没有合适的群或当前容量不足时，保留实机待验。

1. 在原群发送 `/events group`，记录原清单。已有同名样本就先反馈。
2. 在原群分别发送两条新事件，各自等完整回复。第一条 `这是虚构的 R5 验收材料。群共同事件「栖禾展架登记演练」已完成登记表核对，下一步准备登记样本。` 第二条 `这是另一个虚构的 R5 验收群共同事件。「栖禾展架归还演练」已完成归还清单清点，下一步准备归还样本。`
3. 发送 `/events group`。核对出现两张不同编号的新卡，再分别用 `/events group show 编号` 核对作者及两条正文。只对这两张新卡，分别发送 `/events group coordinator 卡片编号 本人QQ账号`，等待各自的协调人设置回执。
4. 在原群发送 `/events group link 登记事件编号 归还事件编号`。两条原话和编号齐全后，复制预览末尾的完整 `/events group link-confirm 操作编号`。成功后等待平时的消息冷却，再重复确认一次，应返回同一操作编号。
5. 分别用 `/events group link-show 登记事件编号` 和 `/events group link-show 归还事件编号` 查询，再在原群发送 `/events group link-undo 操作编号` 与 `/events group link-result 操作编号`。重发原确认应继续返回已撤销。用各自的 `/events group show 编号` 核对原事件仍在。
6. 把两个新卡编号、操作编号和最后回执发到 Codex。保留样本等待对账。

## 对账和清理

后台按原作用域只读核对实际入站、各条完整送达、关联账本、两个原编号、撤销后重试和原始证据。封存后，再用实际编号逐条给出个人 `/events delete` 或原群 `/events group delete` 和本次回执提供的确认命令。清理仅包含本实验新增的卡。群内从未生成两张独立样本时，使用实际结果记录该缺口。
