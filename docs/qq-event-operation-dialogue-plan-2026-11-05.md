# QQ事件操作：语义判断、多轮确认与批量遗忘设计

日期：2026-11-05，America/New_York。本文最初在117r2下形成，用户提出把操作理解与聊天分工，并要求处理“澄清后回答对的”和“忘掉当前所有事件”；当时仅为设计，118轮后缀问题也尚未修复。第121轮已按用户授权实施核心整改，合同调整见第9节，当前部署与真实QQ验收分别以[实施进度](qq-implementation-status.md)为准。

## 1. 执行依据是完整操作上下文

不能只把当前一句“对的”送给模型，也不能把最近一条普通助手回复自动当成授权。输入需要包含：

- 原始操作请求及其真实消息来源；当前用户回复、账号、场合与可信引用关系。
- 主机登记的待处理操作：动作、个人/群范围、单条/多条/全部、原目标及版本、原问句和提问种类。
- 真正已送达的澄清/预览问题及其QQ回执关联。准备中或投递不明的提问不能凭一句“对”自动执行。
- 少量与指代相关的近期用户对话、实际话题引用及当前可访问候选。第一轮模型自行生成的承诺不能作为授权证据。
- 当前权限、主体、成员、控制和来源有效性；由主机提供，不能由模型授予。

只带相关小窗口，不复制完整人设、全部历史、所有来源正文或凭据。模型给出结构化操作候选，主机决定能否执行。

## 2. 明确区分确认目标与确认操作

例：用户先要求忘掉某事，系统问“你是要停止跟进松湖资料这条事件吗？”，用户回复“对的”。原请求已经明确停止意图，已送达问题又绑定同一动作与目标，验证通过后即可执行，无需机械地再问一次。

如果系统只问“你说的是哪件事”，回复只解决目标问题；是否可直接执行取决于原请求已经授权的动作。真正删除仍须展示删除预览；只确认事件名称不等于同意删除正文。批量操作也必须让用户明确知道范围及实际条数。

建议待处理包包含：版本、操作编号、原请求来源、真实账号、会话/群、上下文代次、action、scope、selection、目标ID/revision/source依赖、待答阶段、已送达问题回执、权限版本、过期时间、执行状态。不把昵称作为身份。

状态流：构建→待送达→待澄清/待确认→执行中→成功。拒绝、被新请求替代、过期、版本失效和执行结果不明单独记录；结果不明不能自动重试。

自然回复分为：

| 回复 | 处理 |
| --- | --- |
| 对、对的、是的、没错、确认 | 仅在唯一有效且绑定的待答操作中解释，不重新凭关键词挑事件 |
| 对，但只处理昨天那条 | 修改原选择，生成新计划；不能先按旧计划执行 |
| 是那件事，但不要忘掉 | 确认身份并否定操作，不执行 |
| 不对，是另一件 | 重新解析目标，旧计划不可继续确认 |
| 先别执行、算了 | 撤销待处理操作，不改事件 |
| 与操作无关的聊天 | 正常回答；不让以后无引用的“对”误批旧操作 |

裸肯定只绑定同一账号、同一场合、最近向此人送达且仍有效的操作问题。中间发生本人换题、普通问答问题、重置或新的操作时，不再把裸“对”连到旧问题；显式引用旧问题可在原期限/权限内重新核对。群内其他人的肯定不能代批，继续保持原真正@接收范围。

操作问题应作为独立、可追踪的末尾提问，不在其后再接一个普通聊天疑问让“对”失去指向；正常聊天可以放在问题之前。模型不能改写动作/范围或另问一个竞争问题。仅在该提问部分实际送达后激活确认；发送分段尚未送达、仅有草稿或发送不明，都不授权裸肯定。已执行操作的真实回执仍保持原优先展示原则，不能把待确认问题误当执行成功回执。

沿用现有10分钟确认窗口作为首版上限。每账号/场合只保留一个可裸肯定确认的活动操作，不能出现多条待确认时猜测指向。

## 3. “全部”由主机枚举，不由模型列ID

模型输出类似all_personal的受限选择器，主机依据当前账号和权限生成精确目标快照。默认边界：

| 表达及场合 | 计划范围 |
| --- | --- |
| 私聊“忘掉当前所有事件” | 本人当前保留的个人事件集，跨会话统一；预览明确告知不包括公共群卡和长期记忆 |
| 群内只说“忘掉所有事件” | 先明确个人事件，还是本人对本群公共事件的跟进；不默认替全群清空 |
| “本群所有事件我都不跟进了” | 对本人停止本群公共事件的使用/跟进，其他成员和共同事件正文保持 |
| “个人事件和群聊跟进都忘掉” | 分别列明个人事件与本人可访问群跟进的快照；未核验的群不算已处理 |
| “删除/取消本群全部共同事件” | 必须逐卡满足协调人权限，另行预览；不能用主人身份自动代替各卡协调人 |
| “全部，除了资料截止那条” | 先精确确定例外；例外含糊则不执行，也不先做大部分 |

“当前全部”不限于默认列表的活跃卡，还要覆盖本范围内保留的降温、休眠、暂停、完成/取消等卡，防止终态记录仍被历史问答召回。已停止的计为无需重复变更；到期来源不恢复，不展示不可用正文。high、优先保留等标记不会使本人明确选择的卡免于遗忘。

“忘掉”是停止自动使用和跟进，不悄悄升级为物理删除。批量停止预览说明实际范围、条数、示例和不处理的类别；全部删卡继续完整删除预览确认。群里不因澄清而无意枚举私人事件正文。

批量预览绑定完整ID集合、版本和范围指纹。确认前若增加、减少或改变了目标，不把新目标悄悄加入旧确认，也不把子集处理写成“全部已处理”；重新给出最新预览。确认回复本身不创建新话题，以免制造集合变化。

原权限、来源和待发检查必须延伸到所有投影：本人已遗忘的来源不能经另一投影、原历史、根锚点或归纳重新自动出现；本人停止不等于抹去其他成员已公开的贡献。需要复用或完善面向请求者的依赖失效，不全局篡改公共卡来实现个人遗忘。

## 4. 判断、执行和回答顺序

1. 显式命令和已有确定授权的确认由主机快速处理，保持无需LLM的停止/删除确认通道。
2. 有待处理操作时先判断本条是确认、否定、修订还是换题；目标和范围来自原操作包，不能从一句“对的”重新猜。
3. 无绑定待处理操作、但有潜在操作意图时，将语义判断合并进现有一次话题整理计划，处理对象简称、指称后缀及完整意图。
4. 模型输出无操作/澄清/提议执行等结构化候选，附真实用户原话片段和选择器。高置信度不能代替权限或确认。
5. 主机复核范围、版本、有效来源和审批阶段，执行或登记待确认。执行结果再进入正常主回答，实际回执独立显示。

不先向QQ发出“已经忘记/删除”的自然答复，再另做操作决定。如果先生成草稿，必须缓冲，并根据最终结果修正；首版优先沿用判断→执行→回答，避免多一次重写。

当前话题路由已经可能先于主回答调用模型，不能再无条件追加第三次判定。短肯定且绑定明确时尽量本地处理；需要语义复核的限定回复和模糊管理表达才消耗模型判断。输入沿用现有预算上限，完整操作包过长时缩小候选或澄清，不截掉关键范围/例外。成本须按实际请求与usage对照，不保证百分比或零增加。

## 5. 事务、幂等及失败

- 单条与批量都按原请求/确认来源及操作编号幂等；同一句确认重投不能二次执行。
- 当前同一SQLite内的批量变更事务提交；任一目标失效或权限不足先整体拒绝/重新预览，不静默部分成功。
- 需要跨存储的动作首版不伪称全局原子；事件操作不扩展到聊天删除或长期记忆库。
- 审计保存最小的操作前后控制状态、目标版本、请求/确认关联和计数，便于解释或在新授权下纠错；不复制全文，不自动恢复旧状态或到期来源。
- 模型超时、输出无效、候选不唯一时不写入，正常聊天仍可继续，实际回执明确未执行。
- 问题未送达、确认过期、权限变化或执行中断不能被后来的“对”自动重试；重启保留既有未知结果保护。
- 接续已有10分钟/有界待确认机制及审计容量，不引入无限增长的操作历史。

## 6. 与现有实现的衔接

`qq_action_proposals.py`已有prepared/pending/executing/unknown、送达后待确认、会话/修订绑定及10分钟窗口，可借鉴或扩展公共部分。目前只允许搜索开启和候选保存、限定私聊，肯定词也未覆盖“对的”；不能直接宣称支持事件确认，更不能全局放宽肯定词后让其他操作误触。

事件专用载荷和阶段需要版本化：保留原搜索/记忆建议行为，扩展明确的个人/群事件权限与逐目标版本，群确认绑定真实作者及送达回执。普通模型自然问句不能私自注册执行授权。当前纯命令、删除确认码、本人更正/来源失效和群协调人约束保持兼容。

## 7. 实施顺序和验收

1. 先冻结原字面失败与多轮/批量正反例，定义结构化计划、状态机及事件专用权限合同。
2. 实现待澄清/确认包及送达绑定、短肯定/否定/范围修订、过期/换题/重投/重启保护。
3. 接现有一次路由的语义计划和完整对象归一；同一片段只走一次写入路径，不能被话题更新器与管理器重复处理。
4. 先落地本人全部个人事件的快照预览、事务停止和依赖失效；再接本群本人全部跟进及协调人公共批量管理。未支持的范围明确说明，不能部分执行后说全部完成。
5. 以相同预算做固定语料对照，再分别验收真实QQ。工程、模型和真人三种证据分开，旧真人通过案例不重做。

至少覆盖：后缀简称；澄清后“对的”；确认目标不等于删卡；普通聊天后的“对”；引用旧问题；不同账号/群；对但排除一条；否定及改目标；裸全部/指定范围/例外；混合状态和新旧集合；新卡或版本变化；终态/休眠/高重要度；群个人停止和共同取消差别；无权限/过期/模型失败/重复与重启；历史/摘要/其他投影和待发不回流；部分执行不能虚报全部。

本轮只交付设计，未改业务、配置、事件或启动方式，未发模型/搜索/TTS请求或代理QQ消息。实际启用和验收以实施状态最新记录为准。

## 8. 第120轮整体评审的前置约束

[整体评审](qq-event-system-review-2026-11-05-session120.md)在临时样例确认个人停止后同源群参考仍可向本人回流，以及自动降温单独引起删除预览过期的交互问题。批量遗忘实施前须统一面向请求者的来源/标题/日期/归纳/历史过滤；不可只循环调用单卡状态更新就称为全部遗忘。后续应细化各动作必要的内容/控制/范围版本，区分真实内容变化与纯关注统计变化。该建议尚未改动第3节严格快照合同，不表示已放宽删除校验。

## 9. 第121轮实施合同补充

用户已授权整改，并将正确性置于减少模型调用之前；按[正确性升级指导](qq-event-correctness-upgrade-2026-11-05.md)实施。上文“尚未实施”为119/120轮历史状态，当前代码、部署和真人验收分别查实施进度最新一节。

语义操作允许读取必要的完整候选来源，必要时增加独立结构化判断，不再以必须合并一次路由为硬性门槛。主回答已保存预算保持，未切换模型或凭据。确认快照仍冻结原目标集合，细化为动作相关指纹：正文、来源/到期点、控制状态、协调人、成员及策略变化继续拒绝；纯关注统计和active/cooling变化不独立作废预览。

新的语义与批量计划共用事务执行器，明确命令继续保留原受限实现及回执兼容。尚不宣称所有历史管理入口均已完成内部合并；其后续统一需保留原真实验收行为，并补关联回归。长话题满额和长期维护仍单列，不能与操作会话上线混为完成。

## 10. 第123轮上下文合同

按用户补充，来源标签继承和程序过滤是正常路径，详见[正确性升级第5节](qq-event-correctness-upgrade-2026-11-05.md#5-第123轮统一来源标签和传递合同)。单件与全部遗忘都使相应派生历史失效；不是仅全部遗忘才建立约束。保守上下文屏障仅处理旧无标签来源及已经污染的旧回复，不对每次单件遗忘重置全部新上下文。不启用常态化LLM逐答审核。
