# Qwen3-TTS 连续朗读优化与实测

2026-10-09，在本机 RTX 4090 24GB 上完成。结论：保留原 Qwen3-TTS 1.7B。当前配置在长文本中生成速度约为播放速度的 6.4 倍，真实浏览器连续播放约 93 秒，没有缓冲耗尽造成的断流，因此本轮不需要更换模型。

仍使用原来的 BF16 1.7B 权重、保存的克隆参考音频和文字，没有微调训练，也没有换成 0.6B。此结论针对下面实测文本和配置，不代表所有文本、所有并发量的绝对硬件上限；声音质量没有做正式听评或 ASR 准确率评测。

## 速度与连续播放

RTF = 生成耗时 / 音频时长；小于 1 才能长期跟上播放。以下数据来自实际 GPU 推理。

| 项目 | 音频时长 | 生成耗时 | RTF | 首个 PCM 包 |
| --- | ---: | ---: | ---: | ---: |
| 原 Transformers，同一句短文本 | 6.08 秒 | 11.541 秒 | 1.898 | 完成整段才返回 |
| 优化后，同一句短文本 | 5.76 秒 | 0.956 秒 | 0.166 | 0.167 秒 |
| 优化后，170 字、2 段 | 32.16 秒 | 5.009 秒 | 0.156 | 0.140 秒 |
| 优化后，510 字、6 段 | 92.16 秒 | 14.467 秒 | 0.157 | 0.154 秒 |

短文本为“博士，你回来啦。今天也辛苦了，先休息一下，再和我聊聊天吧。”不同后端的采样音频长度稍有变化，因此不能当成同一个 WAV 的逐帧比较。长文本使用脚本中的 170 字中文段落重复三次；单独短文本、长文本均有 WAV 留存。

另外用真实 Chromium、项目 AudioWorklet 播放器和本地流式接口完成播放，记录如下。这些是浏览器音频时钟的实际结果；与脚本按数据到达时间推算的播放结果分开记录。

| 浏览器场景 | 实际音频 | 首次播放等待 | 播放器断流计数 |
| --- | ---: | ---: | ---: |
| 510 字长文本 | 93.04 秒 | 0.699 秒 | 0 |
| 340 字逐字输出，6 字 / 50ms | 68.40 秒 | 1.438 秒 | 0 |

逐字测试在 3.314 秒完成文字输出，语音在文字完成前开始播放。两条测试短暂重叠仍没有断流。这验证了文字增量到朗读队列的衔接；测试文字由本地诊断页面提供，没有调用外部 LLM，不能据此承诺真实聊天模型的响应时间。

## 实施内容

- 在 WSL Ubuntu 中部署固定版本 vLLM-Omni 0.30.0，启用 v2 执行器、CUDA Graph、异步音频块输出和分阶段 GPU 批处理。没有复制多套 1.7B 工作进程。
- 使用 Linux 文件系统保存运行环境和原权重的校验副本，避免从 Windows 挂载路径导入大量包和读取权重；CUDA 编译组件固定为与运行时匹配的版本，保留编译缓存。
- 服务启动时加载模型并预热当前参考声音。朗读以 24kHz 单声道 PCM 边生成边传输，不再等整段 WAV 完成。
- 浏览器使用 AudioWorklet、连续音频队列和有限缓存。段落依次请求，生成与播放重叠；后端也可调度重叠请求。聊天文字生成完整句子后即可送入朗读队列。
- 停止朗读时取消网络请求和上游 GPU 生成。实际中止测试在约 1 秒处关闭，上游日志确认请求被 Abort，项目状态恢复空闲。模型加载期间断开连接也不会继续提交废弃请求。
- 关闭语音、切换云端提供方或切换原后端时释放原服务，避免常驻显存残留。保留 Transformers 回退和原 WAV 试听接口。

上游机制与接口见 [vLLM-Omni 语音性能优化](https://docs.vllm.ai/projects/vllm-omni/en/latest/design/qwen3_omni_tts_performance_optimization/)、[语音在线服务](https://docs.vllm.ai/projects/vllm-omni/en/latest/user_guide/examples/online_serving/text_to_speech/)及 [Qwen3-TTS 官方项目](https://github.com/QwenLM/Qwen3-TTS)。本页性能数字均为本机实测。

## 当前设置与代价

设置 → Voice 语音已提供推理后端、流式播放、输出第一句后自动朗读、缓冲时长等选项。当前保存的配置为 vLLM-Omni、开启流式播放、缓冲 0.8 秒、闲置释放时间 0（常驻），保留原克隆声音。原“自动朗读回复”偏好为关闭，仍然关闭；需要自动出声时可以自行打开。

冷加载与显存释放也完成实际验证：

- 释放服务：0.882 秒。
- 有持久编译缓存的冷加载，包含参考声音预热：43.493 秒。
- GPU 总占用从 10407 MiB 降至 2392 MiB，重新加载恢复 10407 MiB。语音服务增加约 8015 MiB，即 7.83 GiB。

因此建议聊天时保持常驻。首次安装后的编译更慢；释放后重载也需要等待，不能把冷启动时间算成每一句的正常延迟。另用声音设计模式完成真实 WAV 试听，切换并首次编译共约 61.9 秒，上游该次实际生成约 1.05 秒。

## 验证与复现

本轮相关 Python 测试 51 项、JavaScript 播放测试 13 项全部通过，覆盖设置、流式请求清理、加载后断连、后端释放、聊天增量队列和音频缓冲行为。另有上述真实 GPU、浏览器、取消、声音设计及卸载重载检查。

在项目目录、服务已启动且加速后端可用时执行：

```powershell
python scripts/benchmark_streaming_tts.py
python scripts/create_tts_playback_check.py
```

第二条命令生成被 Git 忽略的本地诊断页面。打开 `http://127.0.0.1:8000/static/_tts_diagnostic.html`，点击“开始长文本朗读”，结束后查看首次播放和 underruns。要检查逐字朗读，打开同一地址加 `?chat=1`，点击“检查逐字输出提前朗读”；该参数只在诊断页面覆盖读取到的自动朗读开关，不保存用户设置。

记录位于 `.runtime/tts-optimized/`：

- `benchmark.json`、`*-arrivals.json`：实际生成和 PCM 到达时间，播放推算字段不作为真实浏览器结果。
- `browser-final-long.json`、`browser-final-chat.json`：真实浏览器结果与截图引用。
- `lifecycle.json`：卸载、冷加载、显存与相同短文本比较。
- `long.wav`、`same-text-comparison.wav`、`design.wav`：本机生成的样本。

安装及回退步骤见 [本地语音部署说明](local-qwen-tts.md)。原后端的速度分析见 [初始性能检查](tts-performance-audit.md)。
