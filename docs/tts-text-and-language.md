# 朗读文本与中英混合处理

2026-10-23 排查的是已经能够生成声音的 TTS 的输入文本，不涉及 GPU 启动故障。

原来的 `cleanSpeech` 只处理少量 Markdown、代码块和动作标签。emoji、ZWJ 组合表情、颜文字以及 `[微笑]`、`:smile:` 会进入模型。另一个风险是直接按字符数切段，可能把 `pronunciation` 等英文单词分成两个请求。

现已在聊天朗读、自动朗读、Voice 试听和服务端音频接口清理表情；图片的 alt 文本不作为正文朗读。常见表情名称只按明确名单删除，普通括号说明、数字、公式和链接文字保留。仅表情的聊天消息不启动语音请求，直接音频接口收到无正文内容时返回明确错误。客户端与服务端共用测试样例，避免两边处理不一致。

语言设置保存为 `Chinese` 时，逐段采用：

- 纯中文：`Chinese`。
- 中文中含英文字母：`Auto`，让模型适配混合文本。
- 纯英文段：`English`。

这只改变当前请求，不修改保存的语言偏好、参考音色和采样参数。用户明确选择的其他语言和 `Auto` 保持原样。按词边界切段，保留小数点，避免常见英文缩写中的句点导致误分句。

`Auto` 是 [Qwen3-TTS 官方支持的语言适配模式](https://github.com/QwenLM/Qwen3-TTS#python-package-usage)。语言适配和完整单词能减少输入层造成的发音风险，不能保证每个专有名词、多音词或缩写都读对，也不能把英文识别器对混合中文音频的错误转写视为发音错误的证明。

验证：Python 39 项、前端朗读与 PCM 播放 25 项通过。当前本机服务使用相同参考音色、固定种子和平静心情，生成了 `你好，请说 hello world，然后继续中文。` 的 Chinese / Auto 两段真实试听，音频时长分别为 4.32 / 3.92 秒。试听和请求参数位于 `.runtime/tts-pronunciation-audit/`。另外保留纯英文对照。音频成功生成不等于英语发音已经由人工确认；系统离线识别器对这两段混合音频的置信度很低，因此未用于宣称发音正确。

刷新网页加载新的 `voice_settings.js`；重启后端后，服务端直接调用和试听的处理也会生效。
